## 3. Script changes (`scripts/bench_vlm.py`) — in priority order

### 3.1 Real windows instead of four unrelated photos (fixes F3)

Add `--windows <json>`: a list of `{window_id, video_id, label (anomaly|normal), gt_event, frame_paths or (video, start_s, end_s)}`.

Build the window set ONCE with a helper `scripts/make_bench_windows.py` (or a `--build-windows` mode). Rules:
- **16 windows: 8 anomalous + 8 normal.**
- Anomalous: from UCF-Crime **test** videos with GT segments (`vad/datasets/ucf_crime.py`). 8 different classes, e.g. Fighting, RoadAccidents, Explosion, Robbery, Shooting, Arson, Burglary, Assault. Window = 4 evenly spaced frames inside the GT segment (use the same "k evenly spaced frames" rule A3 will use).
- Normal: from `manifests/ucf_calib_normal.csv` (train-normal) so normals do not touch the test split. 4 evenly spaced frames from a random 4-8 s span.
- Pick with a fixed seed (0) and write the choice to `notes/vlm-bench-windows.json`. NO hand-picking of "nice-looking" clips, and no re-rolling after you see model outputs.
- Decode with `vad/io/video.py` (sequential grab) at the real frame size (UCF is 320x240). This is the size A5 will see, so the visual token count and latency are representative.
- **Fallback if videos are not downloaded yet** (9.2 GB, `python scripts/download_ucf_crime.py`; check `df -h .`): build 4-frame groups from `data/`, e.g. four of five `danh_nhau_*` for anomalous, four of five `duong_pho_*` for normal, 3 combos per class. Mark every number from the fallback as "static photos, not video windows" in the note. Prefer the real windows: the whole point of A1 is the real workload.

Latency/VRAM timing runs use window #1..N sequentially; use ≥ 8 distinct windows, not the same window repeated.

### 3.2 Warmup and statistics (fixes F2)

- `--warmup 2` (not counted), `--runs 8` measured. Cycle through the windows.
- Report per model: median, mean, p90, min/max of **measured** runs only. Headline = median.
- Log the number of output tokens per run (`len(gen)`) and `s/token`. A model that stops after 40 tokens vs one that hits the 128 cap is not comparable on s/window alone.

### 3.3 Fix the visual token budget (fixes F3, F7)

Latency and VRAM are mostly set by the number of image tokens. Make it explicit and equal across models:
- Qwen2-VL / Qwen2.5-VL: pass `min_pixels`/`max_pixels` to the processor; record `inputs["input_ids"].shape[1]` (prompt tokens) and the image-token count per window. Test two settings: native 320x240 (UCF) and `max_pixels=448*448` upscale cap.
- SmolVLM2: set `do_image_splitting=False` (or the equivalent in the installed transformers) and a fixed `size`/`longest_edge`. Run it once with default splitting too and report both rows. The current 5.57 GB / 31 s is likely default splitting on 4 big images.
- Add the two columns **prompt tokens** and **image tokens** to the result table.
- Also test the **video input** mode for the Qwen models (4 frames as one video; the temporal patch of 2 halves the tokens). One extra row per Qwen model, same windows. If it is faster with equal parse/accuracy, A2 should use it.

### 3.5 Quality sanity metrics (fixes F5)

For every run output, call `vad.verify.vlm.parse_verifier_json` (import it; do not re-implement). Per model, over the 16 windows (use windows, not repeated timing runs), report:

| Metric | Definition |
|---|---|
| `parse_ok_first_try` | fraction of outputs `parse_verifier_json` accepts with no retry |
| `parse_ok_after_fence_strip` | same, informational (regex already tolerates fences) |
| `consistency` | fraction where `is_anomaly == (event_type != Normal)` (catches the Qwen2.5 contradiction) |
| `tpr` / `fpr` | `is_anomaly` vs window label (8 anomalous, 8 normal) |
| `type_match` | on anomalous windows only: parsed `EventType` equals GT class (informational, n=8) |
| `mean_conf_correct` / `mean_conf_wrong` | does confidence carry any signal |

Rules for reading it: n=16 is a **sanity check**, not a ranking. Say so in the note. Report counts (e.g. "7/8"), not percentages alone. Do not choose a winner on a 1-window difference. Do not tune the prompt in A1 (A6 does that, one pass, on different windows).
Keep raw outputs for all 16 windows in the JSON (`outputs: [{window_id, raw, parsed|error}]`).

### 3.6 Per-run time breakdown

Record three timings per run: `preprocess_s` (PIL/processor), `prefill_s` (one forward with `max_new_tokens=1`, or hook), `decode_s`. Simplest honest version: measure `generate` with `max_new_tokens=1` as `prefill_s`, full as `total_s`, `decode_s = total_s - prefill_s`. Then A2/A5 can reason about what shrinks when frames or tokens are cut. Keep `torch.cuda.synchronize()` around each.

### 3.7 Memory methodology (fixes F8, F9)

- Run **each model in its own process** (see §2C.3). Add `--vram-cap-gb` (§2C.4) and make `--out` append per-window JSONL so a Colab disconnect loses at most one window. Always `gc.collect(); torch.cuda.empty_cache()` between variants inside a process.
- Record three numbers per model: `max_memory_allocated` (torch), `max_memory_reserved` (torch), and **device-level peak** from `nvidia-smi --query-gpu=memory.used` sampled every 0.2 s in a background thread during generation. The device number is the one that decides "fits in 6 GB".
- Record `idle_used_gb` (Colab T4 ~0.0; laptop display on 3050 ~0.3-0.6, from the optional local check) so the 6 GB budget is `6.0 - idle_used_gb - 0.4 (context)`.
- Test the **worst case** window, not the average: take the window with the most prompt tokens and report VRAM for it. OOM must be found in the bench, not in A5.
- Keep `load_seconds` meaningful: report `load_seconds` only after weights are in the local HF cache (see §2.5). Put download time in a separate field or skip it.

## 4. Decision procedure (fixes F10, F11)

Apply in this order; write each result into the note.

1. **VRAM gate** (hard, informs whether a 6 GB card is a viable *fallback*): under `--vram-cap-gb 5.5`, worst-case window completes without OOM, and device-level peak on the uncapped run + 0.7 GB margin `< 6.0 GB`. Fail -> that model is not 6 GB-viable. This no longer decides local vs Colab (Colab is chosen); it decides whether the 3050 can serve as a backup for A5 and whether the result is portable.
2. **Quality sanity gate**: `parse_ok_first_try` ≥ 14/16, and `consistency` ≥ 14/16. A model that cannot hold the JSON schema is out regardless of speed, because A2 raises after one retry.
3. **Speed on T4**: report median s/window (post-warmup, real 320x240 windows, real prompt). The task-sheet 3 s rule was written for the 3050 and is no longer the gate; the gate is the capacity check below. If you want to say anything about the 3 s rule, say "T4 median is X.XX s" only.
   - If capacity (step 4) fails, apply one bounded speed fix from §6 and re-measure.
4. **Capacity check** (replaces guessing): ask Thịnh for the expected number of candidate windows `N` at the TH6 freeze (he already has the tier-1 pipeline; a rough count at the current threshold is enough, or use the escalation % target). Compute and tabulate:

   | Setup | s/window | Windows in 8 h overnight | Windows in 3 h evening | Covers N? |
   |---|---|---|---|---|
   | T4 Colab (measured) | median | one session ~3 h = 10800/s (budget 2 h to be safe = 7200/s) | two sessions / account(s) | yes/no |
   | 3050 local | NOT MEASURED (fit only, simulated) | n/a | n/a | n/a |

   Example: 2.5 s x 600 windows = 25 min, fits one Colab session. If N x s/window exceeds ~2 h of one session, split by hash across Phước + Huy (B7) sessions or use the allowed subset (task-assignment §6, measured cost reported). Colab can disconnect, so A3's resumable per-window output is mandatory, not optional.
5. **Final verdict line**, exactly one of:
   - `COLAB T4 GO: <model>, median X.XX s/window on T4, 6 GB-viable: yes|no (simulated), parse n/16, capacity N windows in T min.`
   - `NO-GO: <reason with number>` (then Qwen2.5-VL-3B or a smaller model is re-benched, same procedure).

Qwen2.5-VL-3B stays a **named fallback for quality**, not the primary, unless it beats Qwen2-VL-2B on `type_match`/`tpr` by a margin larger than the n=16 noise (≥ 3 windows).

## 6. Allowed speed fixes if the 3 s rule fails (try ONE round, then re-measure)

Ordered by expected gain / effort:
1. Lower `max_pixels` so 4 frames produce fewer image tokens (UCF is 320x240; do not upscale).
2. Video input mode instead of 4 separate images (temporal patch halves tokens).
3. `attn_implementation="sdpa"` explicitly (check what was used; log it).
4. `max_new_tokens` to p99 of observed output length (EOS already stops early; this only bounds runaway generations).
5. Reduce to 3 frames or 2 frames per window (A3's `k` is configurable). Report the quality cost on the 16 windows.
6. Shorter user prompt (prompt-only; A6 owns prompt tuning, so only trim whitespace/examples that have no effect on schema).

Not allowed in A1: changing quantization scheme to chase speed (bnb nf4 stays), editing `configs/prompts.yaml`, changing `vad/`.
